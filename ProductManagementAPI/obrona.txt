KONTROLERY W ARCHITEKTURZE APLIKACJI - TEORIA I PRAKTYKA
=========================================================

DEFINICJA I ROLA KONTROLERA:
============================

Kontroler (Controller) to fundamentalny element wzorca architektonicznego MVC (Model-View-Controller) 
oraz jego pochodnych w aplikacjach webowych. Jest to klasa odpowiedzialna za:

1. KOORDYNACJA KOMUNIKACJI:
   - Pośrednik między warstwą prezentacji (HTTP API) a logiką biznesową
   - Odbiera żądania HTTP od klientów (frontend, mobile app, inne serwisy)
   - Przekazuje żądania do odpowiednich serwisów biznesowych
   - Formatuje odpowiedzi i zwraca je klientom

2. MAPOWANIE PROTOKOŁU HTTP:
   - Translacja żądań HTTP na wywołania metod biznesowych
   - Mapowanie parametrów URL i body na obiekty domenowe
   - Konwersja wyników biznesowych na odpowiedzi HTTP
   - Obsługa kodów statusu HTTP (200, 201, 404, 500, etc.)

3. WALIDACJA WEJŚCIA:
   - Podstawowa walidacja parametrów żądania
   - Sprawdzanie poprawności formatów danych
   - Autoryzacja i autentykacja (często przez atrybuty)

4. OBSŁUGA BŁĘDÓW:
   - Przechwytywanie wyjątków z warstwy biznesowej
   - Mapowanie błędów domenowych na kody HTTP
   - Formatowanie komunikatów błędów dla klientów

5. SERIALIZACJA/DESERIALIZACJA:
   - Konwersja obiektów .NET na JSON/XML (i odwrotnie)
   - Obsługa różnych formatów danych (Content-Type)
   - Negocjacja zawartości (Content Negotiation)

MIEJSCE W ARCHITEKTURZE N-LAYER:
================================

```
┌─────────────────────┐
│   CLIENT LAYER      │ ← Frontend, Mobile App, API Clients
├─────────────────────┤
│ PRESENTATION LAYER  │ ← KONTROLERY (tu działamy)
├─────────────────────┤
│   SERVICE LAYER     │ ← Business Logic (ProductService)
├─────────────────────┤
│ REPOSITORY LAYER    │ ← Data Access (ProductRepository)
├─────────────────────┤
│   DATABASE LAYER    │ ← MongoDB, SQL Server, etc.
└─────────────────────┘
```

ZALETY UŻYWANIA KONTROLERÓW:
=============================

1. SEPARACJA ODPOWIEDZIALNOŚCI:
   - Kontroler nie zawiera logiki biznesowej
   - Czysta separacja między HTTP a domeną biznesową
   - Łatwiejsze testowanie i utrzymanie

2. REUŻYWALNOŚĆ:
   - Logika biznesowa w serwisach może być używana przez różne kontrolery
   - Możliwość tworzenia różnych interfejsów (Web API, GraphQL, gRPC)

3. TESTOWALNOŚĆ:
   - Unit testy kontrolerów (mockowanie serwisów)
   - Integration testy całych przepływów HTTP
   - Testowanie różnych scenariuszy błędów

4. SKALOWALNOŚĆ:
   - Możliwość rozdzielenia kontrolerów na różne serwery
   - Load balancing na poziomie API
   - Caching odpowiedzi HTTP

WZORCE UŻYWANE W KONTROLERACH:
==============================

1. DEPENDENCY INJECTION:
   - Wstrzykiwanie serwisów przez konstruktor
   - Luźne powiązania między warstwами
   - Łatwiejsze mockowanie w testach

2. COMMAND/QUERY SEPARATION:
   - GET (Query) - pobieranie danych
   - POST/PUT/DELETE (Command) - modyfikacja stanu
   - Optymalizacja pod różne scenariusze użycia

3. DTO PATTERN:
   - Data Transfer Objects dla komunikacji
   - Enkapsulacja danych przesyłanych przez sieć
   - Wersjonowanie API przez różne DTO

4. API RESPONSE WRAPPER:
   - Spójna struktura odpowiedzi (ApiResponse<T>)
   - Standardowe pole błędów i metadanych
   - Ułatwiona obsługa po stronie klienta

KONWENCJE REST API:
===================

Kontrolery implementują zasady REST (Representational State Transfer):

- GET /api/resource - pobieranie kolekcji
- GET /api/resource/{id} - pobieranie elementu
- POST /api/resource - tworzenie nowego elementu
- PUT /api/resource/{id} - aktualizacja całego elementu
- PATCH /api/resource/{id} - częściowa aktualizacja
- DELETE /api/resource/{id} - usuwanie elementu

ANALIZA KONTROLERA ProductsController
==========================================

Kontroler ProductsController jest głównym komponentem warstwy prezentacji w aplikacji ProductManagementAPI, 
implementującym REST API do zarządzania produktami.

LOKALIZACJA:
- Ścieżka: Controllers/ProductsController.cs
- Namespace: ZtpLab1.Controllers
- Endpoint bazowy: /api/v1/products

FUNKCJONALNOŚCI:
================

1. GET /api/v1/products - GetProducts()
   - Pobiera listę wszystkich produktów (tylko ID i nazwa)
   - Zwraca podstawowe informacje o produktach
   - Metoda asynchroniczna
   - Zwraca typ: ActionResult<ApiResponse<IEnumerable<object>>>

2. GET /api/v1/products/{id} - GetProduct(id)
   - Pobiera szczegółowe informacje o konkretnym produkcie
   - Parametr: string id (identyfikator produktu)
   - Zwraca 404 jeśli produkt nie istnieje
   - Zwraca typ: ActionResult<ApiResponse<Models.Product>>

3. POST /api/v1/products - CreateProduct()
   - Tworzy nowy produkt z walidacją domenową
   - Parametr: CreateProductDto createDto
   - Zwraca 201 Created z lokalizacją nowego zasobu
   - Wykorzystuje wzorzec Specification do walidacji
   - Zwraca typ: ActionResult<ApiResponse<Models.Product>>

4. PUT /api/v1/products/{id} - UpdateProduct()
   - Aktualizuje istniejący produkt
   - Parametry: string id, UpdateProductDto updateDto
   - Pełna walidacja domenowa przy użyciu wzorca Specification
   - Zwraca zaktualizowany produkt
   - Zwraca typ: ActionResult<ApiResponse<Models.Product>>

5. DELETE /api/v1/products/{id} - DeleteProduct()
   - Usuwa produkt z bazy danych
   - Parametr: string id
   - Zwraca komunikat o sukcesie operacji
   - Zwraca typ: ActionResult<ApiResponse>

5. Wersjonowanie API:

   - Przygotowanie na przyszłe wersje API

6. Asynchroniczne programowanie:
   - Wszystkie operacje są asynchroniczne (async/await)
   - Optymalizacja wydajności aplikacji
   - Non-blocking operations

SYSTEM WALIDACJI I WZORZEC SPECIFICATION PATTERN
================================================

TEORIA WZORCA SPECIFICATION:
============================

Wzorzec Specification Pattern to wzorzec projektowy Domain-Driven Design (DDD), 
który enkapsuluje reguły biznesowe w postaci obiektów specyfikacji.

DEFINICJA I CELE:
=================

1. ENKAPSULACJA REGUŁ BIZNESOWYCH:
   - Każda reguła biznesowa jest oddzielnym obiektem
   - Reguły można komponować, testować i ponownie używać
   - Separacja logiki walidacji od logiki aplikacyjnej

2. COMPOSABILITY (KOMPONOWALNOŚĆ):
   - Łączenie prostych specyfikacji w złożone reguły biznesowe
   - Operatory logiczne (AND, OR, NOT) między specyfikacjami
   - Budowanie kompleksnych walidacji z prostych bloków

3. TESTOWANIE REGUŁ:
   - Każda specyfikacja może być testowana niezależnie
   - Unit testy dla konkretnych reguł biznesowych
   - Łatwiejsze debugowanie złożonych walidacji

4. REUŻYWALNOŚĆ:
   - Ta sama specyfikacja w różnych kontekstach
   - Możliwość użycia w różnych serwisach i kontrolerach
   - Centralizacja definicji reguł biznesowych

ARCHITEKTURA SYSTEMU WALIDACJI W PROJEKCIE:
===========================================

```
┌─────────────────────────────────┐
│        ISpecification<T>        │ ← Interfejs bazowy
├─────────────────────────────────┤
│   - IsSatisfiedBy(T item)       │
│   - GetValidationErrors(T item) │
│   - SpecificationName           │
└─────────────────────────────────┘
                 ▲
                 │
┌─────────────────────────────────┐
│     BaseSpecification<T>        │ ← Klasa abstrakcyjna
├─────────────────────────────────┤
│   + IsSatisfiedBy() - virtual   │
│   + GetValidationErrors() - abs │
└─────────────────────────────────┘
                 ▲
        ┌────────┴────────┐
        │                 │
┌───────────────┐ ┌──────────────┐
│  PRODUKTY     │ │ FORBIDDEN    │
│  - Name       │ │ WORDS        │
│  - Price      │ │ - Word       │
│  - Quantity   │ │ - Length     │
│  - ForbWords  │ └──────────────┘
└───────────────┘
```

ANALIZA IMPLEMENTACJI W PROJEKCIE:
==================================

1. INTERFEJS ISpecification<T>:
   - Generyczny interfejs dla wszystkich typów walidacji
   - IsSatisfiedBy() - sprawdza czy obiekt spełnia kryteria
   - GetValidationErrors() - zwraca szczegółowe błędy
   - SpecificationName - nazwa dla diagnostyki

2. KLASA BAZOWA BaseSpecification<T>:
   - Implementuje domyślną logikę IsSatisfiedBy()
   - Używa GetValidationErrors() do sprawdzenia poprawności
   - Abstrahuje wspólną funkcjonalność

3. KOMPOZYTOWA SPECYFIKACJA - CompositeSpecification<T>:
   - Łączy wiele specyfikacji w jedną
   - Metoda And() do dodawania kolejnych reguł
   - Zbiera błędy ze wszystkich specyfikacji składowych

KONKRETNE SPECYFIKACJE W PROJEKCIE:
===================================

1. PRODUKTY - 4 SPECYFIKACJE:
   
   a) ProductNameSpecification:
      - Długość nazwy: 3-20 znaków
      - Tylko litery i cyfry (regex: ^[a-zA-Z0-9]+$)
      - Brak spacji i znaków specjalnych
      - Trim() nazwy przed walidacją
   
   b) ProductPriceSpecification:
      - Cena większa od 0
      - Maksymalna cena (np. 999999)
      - Walidacja typu decimal
   
   c) ProductQuantitySpecification:
      - Ilość >= 0 (może być 0 - brak na stanie)
      - Typ int, liczby całkowite
   
   d) ProductForbiddenWordsSpecification:
      - Sprawdza aktywne zabronione słowa
      - Case-insensitive porównanie (ToLowerInvariant())
      - Contains() do znajdowania słów w nazwie
      - Zwraca listę znalezionych zabronionych słów
      - Dodatkowa metoda GetForbiddenWordsInName()

2. ZABRONIONE SŁOWA - 1 SPECYFIKACJA:
   
   a) ForbiddenWordSpecification:
      - Długość słowa: 2-50 znaków
      - Nie może być puste ani składać się z białych znaków
      - Opcjonalny opis powodu: maksymalnie 500 znaków
      - Walidacja Trim() przed sprawdzeniem

INTEGRACJA Z VALIDATION RESULT:
===============================

System używa standardowego ValidationResult z .NET:
- Strukturalne błędy z opisem i nazwą właściwości
- Możliwość zwrócenia wielu błędów naraz
- Integracja z ModelState w kontrolerach
- Czytelne komunikaty dla użytkowników

ZALETY IMPLEMENTACJI:
=====================

1. SEPARATION OF CONCERNS:
   - Reguły biznesowe oddzielone od logiki kontrolerów
   - Każda specyfikacja ma jedną odpowiedzialność
   - Łatwiejsze utrzymanie i rozwój

2. OPEN/CLOSED PRINCIPLE:
   - Łatwe dodawanie nowych specyfikacji
   - Bez modyfikacji istniejącego kodu
   - Rozszerzalność systemu walidacji

3. TESTOWANIE:
   - Unit testy dla każdej specyfikacji osobno
   - Mockowanie zależności (lista zabronionych słów)
   - Testowanie kompozycji specyfikacji

4. PERFORMANCE:
   - Early return w przypadku błędów krytycznych
   - Lazy evaluation - sprawdzanie tylko aktywnych słów
   - Efektywne algorytmy (Contains, Regex)

5. ELASTYCZNOŚĆ:
   - Dynamiczne ładowanie zabronionych słów
   - Możliwość włączania/wyłączania reguł
   - Konfigurowalność przez bazę danych

UŻYCIE W SERWISACH:
===================

```csharp
// Kompozycja specyfikacji w ProductService
var specifications = new CompositeSpecification<Product>()
    .And(new ProductNameSpecification())
    .And(new ProductPriceSpecification())
    .And(new ProductQuantitySpecification())
    .And(new ProductForbiddenWordsSpecification(forbiddenWords));

var errors = specifications.GetValidationErrors(product);
```

WZORZEC SPECIFICATION vs. DATA ANNOTATIONS:
===========================================

SPECIFICATION PATTERN:
- Złożone reguły biznesowe z kontekstem
- Dynamiczne walidacje (np. lista zabronionych słów)
- Komponowalność i reużywalność
- Testowanie jednostkowe reguł

DATA ANNOTATIONS:
- Proste walidacje formatów i zakresów
- Statyczne reguły na poziomie modelu
- Integracja z ModelState
- Mniejszy overhead dla prostych przypadków

System łączy oba podejścia dla maksymalnej elastyczności i wydajności.

    [Required] decimal Price,
    int Quantity = 0

{

## KLUCZOWE KONCEPTY I WZORCE
=============================

### **1. DEPENDENCY INJECTION (Wstrzykiwanie Zależności)**

**Co to:** Zamiast tworzyć obiekty wewnątrz klasy, dostarczamy je z zewnątrz

**Tradycyjnie (źle):**
```csharp
public class ProductService
{
    private ProductRepository _repo = new ProductRepository(); // ❌ Źle!
}
```

**Z Dependency Injection (dobrze):**
```csharp
public class ProductService
{
    private readonly IProductRepository _repo;
    
    public ProductService(IProductRepository repo) // ✅ Dobrze!
    {
        _repo = repo;
    }
}
```

**Zalety:** Łatwiejsze testowanie, luźne powiązania, możliwość zamiany implementacji

### **2. SPECIFICATION PATTERN (Wzorzec Specyfikacji)**

**Co to:** Enkapsulacja reguł biznesowych w osobnych obiektach

**Problem:** Jak sprawdzić czy produkt jest poprawny?
```csharp
// ❌ Źle - logika rozproszona po całym kodzie
if (product.Name.Length < 3) return "Za krótka nazwa";
if (product.Price <= 0) return "Zła cena";
if (forbiddenWords.Contains(product.Name)) return "Zabronione słowo";
```

**Rozwiązanie:** Specification Pattern
```csharp
// ✅ Dobrze - każda reguła w osobnej klasie
var nameSpec = new ProductNameSpecification();
var priceSpec = new ProductPriceSpecification(); 
var forbiddenSpec = new ProductForbiddenWordsSpecification(forbiddenWords);

var errors = nameSpec.GetValidationErrors(product)
    .Concat(priceSpec.GetValidationErrors(product))
    .Concat(forbiddenSpec.GetValidationErrors(product));
```

**Zalety:** Reużywalność, testowalność, czytelność kodu

### **3. REPOSITORY PATTERN (Wzorzec Repozytorium)**

**Co to:** Abstrakcja dostępu do danych

**Bez Repository:**
```csharp
// ❌ Service bezpośrednio używa MongoDB
public class ProductService
{
    public async Task<Product> GetProduct(string id)
    {
        var collection = database.GetCollection<Product>("Products");
        return await collection.FindAsync(x => x.Id == id);
    }
}
```

**Z Repository:**
```csharp
// ✅ Service używa abstrakcji
public class ProductService
{
    private readonly IProductRepository _repository;
    
    public async Task<Product> GetProduct(string id)
    {
        return await _repository.GetByIdAsync(id);
    }
}
```

**Zalety:** Możliwość zmiany bazy danych, łatwiejsze testowanie, separacja odpowiedzialności

### **4. DTO PATTERN (Data Transfer Objects)**

**Co to:** Obiekty do przesyłania danych między warstwami

**Dlaczego nie wysyłać bezpośrednio modeli?**
```csharp
// ❌ Model z bazy - zawiera ID, metadane itp.
public class Product
{
    public string Id { get; set; }              // Nie potrzebne przy tworzeniu
    public DateTime CreatedAt { get; set; }     // Nie potrzebne przy tworzeniu
    public string Name { get; set; }
    public decimal Price { get; set; }
}
```

**DTO dla konkretnego przypadku:**
```csharp
// ✅ DTO - tylko to co potrzebne
public class CreateProductDto
{
    public required string Name { get; init; }    // Tylko nazwa
    public required decimal Price { get; init; }  // Tylko cena
    // Brak ID - wygeneruje się automatycznie
}
```

**Zalety:** Kontrola nad tym co wysyłamy/odbieramy, walidacja, wersjonowanie API

## REST API - KONWENCJE I ENDPOINTY
===================================

**REST** = Representational State Transfer - zestaw reguł jak budować API

### **NASZE ENDPOINTY:**

#### **PRODUKTY:**
- `GET /api/v1/products` → Lista wszystkich produktów
- `GET /api/v1/products/{id}` → Jeden konkretny produkt  
- `POST /api/v1/products` → Utwórz nowy produkt
- `PUT /api/v1/products/{id}` → Zaktualizuj produkt
- `DELETE /api/v1/products/{id}` → Usuń produkt

#### **ZABRONIONE SŁOWA:**

- `GET /api/v1/forbidden-words/active` → Tylko aktywne słowa
- `GET /api/v1/forbidden-words/{id}` → Jedno słowo
- `POST /api/v1/forbidden-words` → Dodaj nowe słowo
- `PUT /api/v1/forbidden-words/{id}` → Zaktualizuj słowo  
- `DELETE /api/v1/forbidden-words/{id}` → Usuń słowo
- `PATCH /api/v1/forbidden-words/{id}/toggle` → Przełącz aktywność

### **KODY ODPOWIEDZI HTTP:**
- **200 OK** → Operacja udana
- **201 Created** → Zasób utworzony pomyślnie
- **400 Bad Request** → Błędne dane wejściowe
- **404 Not Found** → Zasób nie istnieje
- **500 Internal Server Error** → Błąd serwera

## WALIDACJA I REGUŁY BIZNESOWE
===============================

### **WALIDACJA NA POZIOMIE DTO (Data Annotations):**
```csharp
public class CreateProductDto
{
    [Required(ErrorMessage = "Nazwa jest wymagana")]
    [StringLength(20, MinimumLength = 3)]
    public required string Name { get; init; }
    
    [Range(0.01, double.MaxValue)]
    public required decimal Price { get; init; }
}
```

### **WALIDACJA BIZNESOWA (Specification Pattern):**

#### **1. Walidacja nazwy produktu:**
- Długość: 3-20 znaków
- Tylko litery i cyfry (regex: `^[a-zA-Z0-9]+$`)
- Bez spacji i znaków specjalnych

#### **2. Walidacja ceny:**
- Musi być > 0
- Maksymalna wartość (np. 999999)

#### **3. Walidacja zabronionych słów:**
- Sprawdzanie czy nazwa zawiera aktywne zabronione słowa
- Case-insensitive (spam = SPAM = Spam)
- Możliwość włączania/wyłączania słów

## NOWOCZESNE WZORCE C# 11
==========================

### **1. `required` KEYWORD:**
```csharp
public class CreateProductDto
{
    public required string Name { get; init; }  // ✅ Musi być podane!
}

// Użycie:
var dto = new CreateProductDto { Name = "Produkt" }; // ✅ OK
var bad = new CreateProductDto { }; // ❌ BŁĄD KOMPILACJI!
```

### **2. `init` ACCESSORS:**
```csharp
public string Name { get; init; } // Można ustawić tylko przy tworzeniu

var dto = new CreateProductDto { Name = "Test" };
dto.Name = "Nowa nazwa"; // ❌ BŁĄD KOMPILACJI - immutable!
```

**Zalety:**
- **Compile-time safety** → Błędy przy kompilacji, nie w runtime
- **Immutability** → Objects nie mogą być zmieniane po utworzeniu  
- **Thread safety** → Bezpieczne w wielowątkowości
- **Performance** → Brak setterów w runtime
